## 0. Summary

Route A (official REST) needs a Learn administrator: `By default, NO integrations are enabled and the Learn server will not allow integrations without a Learn Administrator taking action` [vendor AD blackboard/rest-apis/getting-started/framework.md:27]. No student-only path appears in any fetched document. A request costs one email and the draft is in §1; if granted, three-legged OAuth with the `offline` scope would decouple the sync from the Entra clock entirely.

Route B (cookie from Node) is real and repeated: at least six independent open-source clients do it, two of them MCP servers on Microsoft-SSO tenants. Reads probably need only `Cookie`; `X-Blackboard-XSRF` is needed for writes. Expiry shows as 401, or a 3xx to a login path, or a 403 whose body names the session. The session's own clock is readable and extendable through two internal utility endpoints. Whether SU's cookie lives 3 h, 8 h or a day is still unmeasured.

Entra decides everything after that: `ESTSAUTHPERSISTENT` is the only Microsoft cookie that survives a browser restart, and Conditional Access can shorten or forbid it.

Mobile route: not pursued. Rate limits: none documented for cookie clients; stay sequential. Policy: the SU AUP text I could reach is silent on automation; SU's AI guidelines are not.

## 1. Route A — official REST

**Standard practice.** A developer registers an application in the Anthology developer portal and receives a key, secret and Application ID; a Learn administrator then creates a "REST API Integration" using that Application ID and a Learn user to act as [vendor framework.md:36-64]. The rule, verbatim: `A Learn Administrator must enable each app from the Learn Admin Panel before access is granted` [framework.md:25]. Acting as an ordinary user needs three-legged OAuth (3LO), and the admin must set `End User Access` to Yes: `End users will sign in with their own Learn ID to use the integration. Each user's access is then limited to his or her own permissions` [vendor rest-and-learn.md:47]. Scopes are `read, write, delete, and/or offline`; `offline` is what yields refresh tokens, so the user need not log in again [vendor 3lo.md:39, 87-101]. Bearer tokens last one hour [framework.md:98].

**Examples (fetched).** 3LO endpoints `GET /learn/api/public/v1/oauth2/authorizationcode` then `POST .../oauth2/token`, with PKCE since Learn 3700.4 [vendor 3lo.md:31, 66, 115-138]; the doc's own worked example is a student "GetMyGrades" mobile app [3lo.md:27-31]. Third-party MCP/SDK projects mirror the flow (`metorial/metorial integrations/blackboard/src/auth.ts` and `shurrey/blackboard-learn-sdk-generator`, seen in GitHub code-search snippets only). felipedias-ie's README states the consequence plainly: the documented API `requires an OAuth application registered and approved by your institution's Blackboard administrator. Most students and many staff can't get one` [code FD README.md:21-23]; campus-cli says it "needs no OAuth developer key from your university" [code campus-cli README.md:18]. Both are maintainers' claims, not vendor text.

**Pitfalls.** (1) Developers are `limited to non-production testing pursuant to the applicable REST Developer Agreements` [framework.md:23]; a personal app registered by a student has no SU data until SU approves it. (2) With End User Access = Yes the form still asks for a "Learn user" [rest-and-learn.md:43-49], so the admin has a decision to make, not a checkbox. (3) Public v1 only: the crawler's internal calls (gradebook `grades?expand=…`, `calendarItems`, attempts) are out of scope of a token (parity is S3-R2). (4) 10,000 requests per 24 h per developer group, token bucket, 429 with `Retry-After` [vendor developer-portal/rate-limit-migration.md:15, 39-49] — ample for one student.

**SU's process.** Answers "Blackboard Integrations" (blackboard01 space, page 154387055) [summary]: some integrations are installed `at the request of campus users`, Online Learning Services installs and maintains them "to the best of their ability" but they are unsupported by ITS, with support from Academic Applications and Platforms; the Support Contacts page names help@syr.edu with "Blackboard" in the subject [summary; also `[repo]` 108 §A.7]. I could not read the page, so whether a *personal* integration is even a request type is unverified.

**Maps onto this stack.** If granted: the client library gets a second auth strategy (bearer + refresh token) behind the same endpoint functions; the sync becomes independent of Entra and Duo (unverified: how long an `offline` refresh token lives at SU). It cannot cover internal-only calls, so route B stays for those.

**Draft request (Stack sends it, or not; 107 Q4).**
> To: help@syr.edu — Subject: Blackboard — request to enable a personal read-only REST integration. Hello, I am [name], NetID [x]. I would like Online Learning Services to consider enabling one personal REST integration in SU's Blackboard Learn so that a small program on my own laptop can read my own course data (my courses, content, my gradebook entries, announcements and calendar) instead of my copying it by hand. It would use the developer-portal three-legged OAuth flow with End User Access = Yes, so it acts only as me, sees only what my account sees, and I would grant scope `read` (plus `offline`, so I need not re-authenticate through SSO each day). It is single-user, read-only, sequential and slow, stores nothing about anyone else, and needs no elevated Learn user. I would register the application in the Anthology developer portal and send you the Application ID. If SU cannot enable this, could you also tell me whether read-only automated access to my own account through my own logged-in session is acceptable use? Thank you.

**Verdict.** Not available to a student alone; **worth the one email in parallel** (it also elicits a written policy answer, which 107 Q10 needs), never a dependency of the sprint.

## 2. Route B — cookie session from Node

**Standard practice.** Log in once in a real browser, keep Blackboard's cookies, replay them from an HTTP client. Every client below does so.

**Examples (fetched).**
- **Cookies.** `BbRouter` and `JSESSIONID` are the auth cookies [code CC auth/login.ts:92-93; FD src/auth/session.ts:16 `REQUIRED_COOKIE_CANDIDATES`]. The Fitchburg script also carries `AWSALB`, `AWSALBCORS` (load-balancer stickiness) [code mroberts1/fsu-interactive-media-fa26 `script/blackboard:299`]: send the whole Blackboard-host jar, not two names. `BbRouter` is HttpOnly, so `document.cookie` cannot see it [code same repo AGENTS.md ~L438; FD README.md:110]; one userscript reads it from `document.cookie` anyway (AmirbarrabajaLeon/blackboard-ultra-course-exporter, search snippet) — conflicting, tenant-dependent, unverified for SU.
- **BbRouter is a comma list.** `expires:<epoch s>`, `timeout:<s>`, `xsrf:<uuid>`, plus id/signature fields [code kartikk221/cuny-blackboard-api `src/modules/blackboard/authentication.ts:143-158`; edulinq/lms-toolkit `backend.py` cookie parser; CC login.ts:36 `/expires:(\d+)/`, :85 `/xsrf:([a-f0-9-]+)/`]. campus-cli accepts an expiry only if it is future and under 24 h, else falls back to 3 h (`SESSION_TTL_FALLBACK_MS`, login.ts:12, 33-45).
- **`X-Blackboard-XSRF`.** It is the `xsrf:` value from `BbRouter`, echoed as a header. Tested on a Microsoft-SSO tenant: `Without it every write is 403 {"message":"This request is not associated with a valid session."} while reads keep working` [code mroberts1 AGENTS.md ~L435-438]. felipedias-ie adds it, plus `Origin` and `Referer: <base>/ultra`, only for non-GET [code FD src/client/http.ts:208-215]. campus-cli sends it on every call when it holds a token (CC api/client.ts:132); cuny-blackboard-api sends it on the GET to `utilities/timeUntilBbSessionInactive` (authentication.ts:91-95). Conclusion: reads work without it on the tenants tested; **not verified on SU's internal v1** — `scripts/bb-probe.mjs:118` already tests each `/learn/api/v1` path with and without it, which settles it.
- **What expiry looks like.** No single answer; the clients handle all three. 401 → `SESSION_EXPIRED` (CC client.ts:176-179; FD http.ts:278-281). A 3xx whose `Location` is a login path (`/webapps/login`, `/auth-saml/saml/login`, `/adfs/ls`, `/login.jsp`, `/oidcAuth`) or a final URL on one → expired (FD http.ts:47-53, 256-262, 276). A 403 counts as expired only if the body matches `/session|login|authenticat/i`; otherwise it is a real permission gap (FD http.ts:279-281). cuny-blackboard-api uses `redirect: 'error'` so a bounce throws (authentication.ts:91). **A 200 HTML login page is not handled or documented by any of them** — unverified; the client should treat any non-JSON `Content-Type` on `/learn/api/` as expiry.
- **The session's own clock.** `GET /learn/api/v1/utilities/timeUntilBbSessionInactive` returns `timeBeforeTimeout` (ms); `.../utilities/keepBbSessionActive` extends it [code FD src/client/endpoints.ts:31,33; FD src/client/index.ts:139-160; cuny authentication.ts:88-119]. The reply carries `Set-Cookie`, so a stored jar must absorb rotated cookies (FD http.ts:324-331). Lifetimes seen: `timeout:28800` = 8 h at Fitchburg (mroberts1 AGENTS.md ~L430; `script/blackboard:20`), `timeout:10800` = 3 h at UPC (CC login.ts:12), "about three hours" in felipedias-ie's README:69. These are *inactivity* timers; felipedias-ie itself notes an "absolute-lifetime cap" can still expire a session (index.ts:167-172). SU's value is unmeasured.
- **User-Agent / Origin.** No source shows either being enforced on GETs. felipedias-ie replays the browser's captured UA (session.ts:25, 46); jwd3t/Blackboard-CLI uses a Mozilla UA (auth.py:51); campus-cli's axios client sets none (client.ts:126-133), so Node's default `axios/…` UA goes out (inferred, unverified). A bb2dash UA (`bb-probe.mjs:74`) is untested at SU.
- **Silent renewal without a browser.** felipedias-ie replays the SAML redirect chain over plain HTTP (`/ultra → /auth-saml/saml/login → login.microsoftonline.com (auto-submit SAMLResponse) → /auth-saml/saml/SSO → /ultra`) using Entra cookies imported from the browser [code FD README.md:69-87]. campus-cli instead reopens its persistent Playwright profile headless at `SAML_URL` with a 20 s timeout (login.ts:301-333).

**Pitfalls.** Cross-host redirects (`bbcswebdav` → CDN) must drop `Cookie` and the XSRF header (CC client.ts:135-143; same idea as `ingest/fetch_signed.mjs` [repo, 108 §A.4]). A request whose absolute URL points off-host would leak the jar: enforce the origin at one choke point (CC client.ts:20-32, 159). campus-cli's `SAML_URL` carries a tenant-specific `apId` (login.ts:10); SU's is unknown (unverified; it appears in the redirect a logged-out `GET /ultra` receives).

**Maps onto this stack.** `bb login` = Playwright persistent profile (107 Q5); the client stores the Blackboard-host jar (0600), parses `BbRouter` for expiry, XSRF only on non-GET. `whoami` should call `timeUntilBbSessionInactive` next to `public/v1/users/me`: it gives Task 0 a cheap, secret-free lifetime reading. The probe (Q16) could also print `BbRouter`'s `timeout` and `expires` minus now (numbers, not the cookie).

**Verdict.** Feasible and well-trodden; **the recommended route**. Open: SU's session lifetime and whether the internal-v1 set answers with just the cookie (the probe).

## 3. The Entra side

**Standard practice.** Microsoft's cookie table: `ESTSAUTH` — session information for SSO, "Transient"; `ESTSAUTHPERSISTENT` — same, "Persistent"; `ESTSAUTHLIGHT` — a sign-out helper [ms authentication/concept-authentication-web-browser-cookies.md:22-24]. A persistent cookie exists only if the user answers Yes to "Stay signed in?" or an admin enables Persistent browser session: `Without any session lifetime settings, the browser session has no persistent cookies` [ms authentication/concepts-azure-multi-factor-authentication-prompts-session-lifetime.md:43]. The Yes answer `sets a persistent cookie … remembers both first and second factors, and it applies only for authentication requests in the browser` [same :62]. Default lifetime: the doc states a `rolling window of 90 days` for sign-in frequency [same :14; ms conditional-access/concept-session-lifetime.md:29]; a search summary of an Entra write-up gives "up to 90 days" for the KMSI cookie against 24 h for non-persistent [summary, office365itpros.com]. Treat 90 days as Microsoft's ceiling, not SU's setting.

**What an institution can shorten.** (a) *Sign-in frequency*: how long before re-authentication, hours to days or every time [ms concept-session-lifetime.md:25-27]. It reaches SAML apps like Blackboard `as long as they don't drop their own cookies and regularly redirect back to Microsoft Entra ID` [same :45]: when Blackboard's session dies, the browser bounces to Entra, and Entra then decides between silent re-mint and interactive sign-in. (b) *Persistent browser session* = "Never persistent" (or "Always"); the policy `overwrites` the user's Stay-signed-in answer [ms conditional-access/howto-conditional-access-session-lifetime.md:60; mfa doc :66, :88]; the "Never" wording is [summary]. (c) Legacy "Remember MFA" of 1–365 days [mfa doc :74]. The user sees none of these settings.

**Two clocks.** A re-mint works only while the Entra session is younger than sign-in frequency and the persistent cookie still exists. Blackboard's own inactivity timer (§2) is the second clock. This explains "22–23.5 h survivals against a 4 h death" without contradiction (`[repo]` 107 §2): different clocks won on different days.

**Maps onto Task 0.** Both routes B and C sit on these clocks; the MCP changes nothing (107 §2). A cheap addition: after a login, list the profile's cookie **names, hosts and expiries, never values** (campus-cli's `getSsoExpiry` does exactly this, login.ts:67-80). `ESTSAUTHPERSISTENT` present with expiry near +90 d means persistence is allowed and only sign-in frequency can bite; absent after answering Yes means "Never persistent" is enforced (Stack's "never works"). Unverified, worth testing: Chromium persistent contexts drop session-only cookies (`ESTSAUTH`) at close, so only the persistent cookie carries a headless re-mint; campus-cli's SSO expiry accounts for cookies with `expires > 0` only (login.ts:73-77). Discrepancy: the repo says "Duo"; SU-hosted pages in search summaries describe a Microsoft sign-in with an Authenticator code, and Duo only for DMC/MySlice [summary]. Task 0 should record which prompt appears.

**Verdict.** The re-mint route is real but policy-gated; it cannot be predicted from outside. Task 0's numbers plus the cookie-expiry listing decide it.

## 5. Rate limits and etiquette

**Documented.** The only vendor limit is for portal-registered apps: 10,000 calls per 24 h, token bucket, 429 with `Retry-After`, `X-Rate-Limit-Limit/-Remaining` [vendor rate-limit-migration.md:15, 39-49; framework.md:117-133]. Nothing shows it applies to a cookie session (unverified).

**Observed elsewhere.** felipedias-ie: concurrency 4, a minimum gap between starts, 429 → back off, `Retry-After` honoured up to 5 s (http.ts:58, 143-156, 294-299). campus-cli: API lane 4 concurrent, downloads strictly serial with a 350 ms gap, "the cost of being wrong is … the university blocking the address" (CC api/pace.ts:1-25). Neither reports a 429 actually seen. Ultra's own request rate: no measurement found (campus-cli asserts the UI fires several in parallel, pace.ts:12-13; unverified).

**Here.** No 429 was ever seen (107 §2); the crawler has no `Promise.all` and issues attempts "one at a time" (`ingest/bb_crawler.js:510`). Keep that: strictly sequential, `Retry-After` honoured, stop the run after three consecutive 429s or any 403 that is not a permission gap, bb2dash `User-Agent`, never more than the Ultra UI loads (107 Q10 default).

**Verdict.** No limit to design around; etiquette by construction.
